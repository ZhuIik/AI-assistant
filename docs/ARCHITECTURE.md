# Архитектура и технологии

Этот документ объясняет не только *что* делает каждая часть системы, но и *почему* она устроена именно так — какие альтернативы рассматривались и почему выбор пал на текущее решение. Ориентирован на человека, который впервые видит проект и хочет понять его целиком, а не только API.

## Общая идея: RAG, а не дообучение модели

Ключевое архитектурное решение проекта: ответы строятся через **Retrieval-Augmented Generation** (поиск релевантного контекста + генерация поверх него), а не через дообучение (fine-tuning/LoRA) модели под материалы курса.

**Почему не LoRA/QLoRA:**
- **Мультитенантность.** Систему используют разные преподаватели с разными курсами. LoRA/QLoRA потребовал бы отдельный адаптер под каждый курс — то есть полноценный ML-пайплайн (сбор датасета → обучение → merge → конвертация под инференс-движок) на каждую загрузку материалов, вместо "загрузил видео и готово".
- **Объём данных мал для дообучения.** Ожидаемый масштаб курса — до ~100 видео и пособий. Дообучение на таком объёме либо не даёт эффекта, либо переобучается под конкретные формулировки лекций (модель начинает дословно повторять фрагменты вместо объяснения).
- **Независимость от инференс-движка.** RAG не зависит от того, чем обслуживается модель — сегодня LM Studio, завтра vLLM. LoRA-адаптер, наоборот, всегда привязан к конкретному формату весов и требует переконвертации при смене движка.

Проект **ранее использовал LoRA** (адаптер для `google/gemma-2-2b-it`, обучающие скрипты на `peft`/`trl`/`bitsandbytes`) — он был полностью удалён при переходе на текущую архитектуру. Если увидите упоминания LoRA в старых материалах/памяти — это уже неактуально.

## Пайплайн данных: от видео до готового к поиску фрагмента

Шаги 1-4 ниже можно запускать по отдельности (полезно для отладки конкретного шага) или одним вызовом `scripts/ingest_lectures.py` — он оборачивает те же самые скрипты и запускает их только для новых файлов, определяя новизну по появлению новых `data/segments/*.segments.jsonl`.

### 1. Транскрибация — `src/audio/whisper_transcriber.py`

**Технология:** faster-whisper (CTranslate2-реализация Whisper) — выбрана вместо оригинального `openai-whisper` из-за значительно более быстрого инференса на том же железе (за счёт квантизации и оптимизированного рантайма), что критично при обработке многочасовых лекций.

Сразу пишет два формата: человекочитаемый `.txt` (для ручной проверки) и структурированный `.segments.jsonl` (start/end таймкоды, спикер, текст) — второй формат используется всем последующим пайплайном.

**Диаризация** (`pyannote.audio`) — опциональна (`--diarize`), так как требует HuggingFace-токен с доступом к gated-модели и заметно увеличивает время обработки. Для лекций с одним основным голосом можно не включать.

### 2. Разметка на смысловые блоки — `scripts/build_annotation_drafts_by_sentence.py`

Сегменты (обычно по 1 фразе) объединяются в более крупные смысловые блоки. **Активная стратегия — нарезка по границам предложений** с целевым размером блока (`--min-chars 800`, `--max-chars 1800`): весь текст лекции сначала склеивается в один поток предложений, затем предложения жадно копятся в блок, пока не будет достигнут `min-chars`, и блок закрывается, как только следующее предложение превысило бы `max-chars`. Чанк **никогда не обрывается внутри предложения**.

**Тайм-коды** для каждого предложения вычисляются отдельно, в общем модуле `scripts/chunking/timed_sentences.py` (используется любой стратегией чанкинга, не только текущей): раз сегмент Whisper даёт тайм-код только на весь сегмент целиком, а не на отдельное предложение внутри него, тайм-код предложения оценивается линейной интерполяцией по позиции символа внутри сегмента. Тайм-код готового блока — это `start` первого и `end` последнего предложения в группе. Это разделение специально сделано так, чтобы будущие стратегии чанкинга (semantic-чанкинг по эмбеддингам соседних предложений, рекурсивный чанкинг и т.д.) могли переиспользовать один и тот же расчёт тайм-кодов, меняя только логику группировки предложений в блок.

**Почему не старая пауза/длительность-эвристика (`scripts/build_annotation_drafts.py`, сохранён в репозитории для сравнения, но больше не часть активного пайплайна):** раньше блоки резались по паузам между репликами, смене спикера и суммарной длине — эвристика, основанная на времени и структуре диалога, а не на смысле. На практике это приводило к катастрофическому числу крошечных, лишённых контекста чанков: на пилотной лекции 46% чанков были короче 200 символов (минимум — 17 символов, `"Ну, у нас не было"`). LLM-аннотация таких обрывков честно отражала их бессодержательность (`topic: "Отсутствие чего-либо"`) — по такому чанку RAG никогда не находился в ответ на реальный вопрос. Замеры (см. раздел "Оценка качества" ниже) подтвердили это численно: `context_recall` подскочил с 0.71 до 0.93 на полном корпусе (14 лекций) после перехода на sentence-based чанкинг — то есть новая нарезка почти вдвое реже "теряет" нужный материал при поиске.

**Почему не фиксированный чанкинг по токенам** (как в стандартных RAG-туториалах, например `RecursiveCharacterTextSplitter`): нарезка по числу токенов рвёт логическую структуру фрагмента лекции безотносительно к предложениям. Текущий подход — компромисс между "не резать предложение" и "не дать чанку разрастись бесконтрольно".

**Ограничение источника данных:** эта стратегия чанкинга (как старая, так и новая) специфична для транскриптов (временная последовательность реплик). Для другого типа источника — учебных пособий (текстовых документов) — она не подходит: там уже есть авторская структура (заголовки, разделы), и чанкинг должен идти по ней. Чанкер для структурированных документов (пособий) — в планах (см. Roadmap).

**Куда это дальше расти:** текущая группировка предложений в блок — чисто механическая (по накопленной длине), без учёта того, меняется ли тема внутри блока. Semantic-чанкинг (векторизовать каждое предложение, сравнивать с соседним по косинусной близости, резать на спаде похожести) и рекурсивный чанкинг обсуждались как следующие кандидаты — оба могут быть добавлены как отдельные скрипты поверх того же `scripts/chunking/timed_sentences.py`, без изменения расчёта тайм-кодов.

### 3. Заполнение метаданных — `scripts/prefill_annotations.py`, `src/llm/annotate.py`

Для каждого блока определяются `topic`, `summary`, `keywords`, `questions`, `cognitive_level`, `interaction_type`, `difficulty`, а текст фрагмента может быть точечно очищен от ошибок распознавания речи.

**Реализация — LLM-вызов с откатом на захардкоженные правила.** По умолчанию каждый фрагмент прогоняется через локальную LLM (`src/llm/annotate.py:annotate_fragment`, тот же локальный сервер, что и для ответов бота): модель читает текст фрагмента и возвращает JSON с `topic`/`summary`/`keywords`/`questions`/`interaction_type`/`cognitive_level` и лёгкой ASR-исправленной версией текста (`cleaned_text`). Промпт явно требует точечных правок, а не пересказа, чтобы не дать модели "довыдумывать" факты сверх сказанного. Оригинальный (до очистки) текст сохраняется рядом в поле `text_raw` — для проверки/отката.

Если LLM недоступна или вернула не-JSON — код автоматически откатывается на старые захардкоженные правила (список шаблонов `TOPIC_PATTERNS`, подобранный под конкретный курс, на котором изначально разрабатывался проект) для этого конкретного фрагмента, не прерывая весь прогон. Это тот же fallback-паттерн, что уже используется в `chat.py` (`_extractive_answer`, `_generate_source_summaries`) — деградация до эвристики вместо падения.

**Производительность зависит от двух настроек LM Studio, не связанных с самим кодом:**

1. **GPU Offload** должен быть выставлен на максимум (в настройках модели, Context and Offload). При неполном offload часть слоёв считается на CPU, что резко замедляет генерацию — на практике переход с частичного на полный offload дал ~2x ускорение (100с → 47с/фрагмент на 2B-модели).
2. **Enable Thinking** (Inference → Custom Fields) стоит **выключить**, если модель его поддерживает. Некоторые локальные модели тратят сотни токенов на скрытые "размышления" (`reasoning_content`) перед итоговым JSON-ответом — это не влияет на качество разметки topic/summary/keywords, но кратно увеличивает время генерации. Отключение дало ещё ~2.4x ускорение (47с → 19.5с/фрагмент).

С обеими настройками (полный GPU offload + выключенный Thinking) на практике вышло **~19.5с/фрагмент** последовательно и **~4.7с/фрагмент** при параллельной обработке (`--concurrency 4`, см. ниже) — на курс из ~3000 фрагментов это ~3.9 часа вместо изначальных ~39 часов. `evaluation batch size`/`physical batch size` на эту скорость почти не влияют — они про обработку входного промпта (prefill), а не про потоковую генерацию ответа (decode), которая здесь является узким местом.

`scripts/prefill_annotations.py` поддерживает `--concurrency` (по умолчанию 4, параллельные запросы через `ThreadPoolExecutor` — задача I/O-bound). **Проверено на практике: увеличение выше 4 (пробовали 8, при соответствующем росте Max Concurrent Predictions в LM Studio) не даёт прироста** (~6.3-6.6с/фрагмент что при 4, что при 8) — упор идёт в реальную вычислительную пропускную способность GPU, а не в лимит параллельности запросов. 4 — практический потолок для этой модели/железа; поднимать дальше нет смысла, только держит больше VRAM под параллельные KV-cache. Флаг `--no-llm` даёт мгновенный, но менее точный результат (старые шаблоны) — полезен для отладки без запущенного LM Studio.

Отдельная переменная окружения `ANNOTATE_MODEL` (см. `config.py`) позволяет использовать для этого шага более лёгкую модель, чем для чата (например, `gemma-4-e2b` вместо `gemma-4-e4b`) — быстрее, ценой чуть менее точной разметки.

### 4. Индексация — `scripts/embed_kb.py`, `src/rag/embedder.py`, `src/rag/vector_store.py`

Строит индекс из `data/annotations/*.annotations.jsonl`.

**Embedding-модель:** `text-embedding-nomic-embed-text-v1.5`, обслуживается локально через LM Studio (`EMBED_MODEL` в `config.py`), а не отдельной Python-библиотекой. Multilingual — работает и с русским, и с английским текстом. Раньше использовался `sentence-transformers/all-MiniLM-L6-v2` (лёгкая, но англоцентричная модель, работавшая хуже на русскоязычных лекциях) — заменён, зависимость `sentence-transformers` удалена из `requirements.txt`. Обращение к LM Studio батчится (`src/rag/embedder.py`, по 64 текста за вызов).

**Векторный индекс:** FAISS `IndexFlatL2` — точный полный перебор, без приближённых структур (HNSW, IVF). Осознанный выбор: при ожидаемом объёме (до сотен фрагментов на курс) полный перебор быстрее и точнее приближённых индексов, а approximate-индексы себя оправдывают только на десятках/сотнях тысяч векторов. Векторная БД (Qdrant/Chroma/pgvector) тоже пока избыточна — она нужна при множестве курсов на общем сервере с конкурентным доступом и фильтрацией по course_id на уровне БД, актуально при переезде на сервер, не раньше.

Если `faiss` не установлен, или LM Studio недоступен в момент построения индекса, — `embed_kb.py` всё равно строит индекс, но в чисто лексическом режиме (`manifest.json` с `vector_built: false`). Аналогично `retriever.py` откатывается на лексический поиск, если LM Studio станет недоступен уже в момент запроса пользователя (не только на этапе построения индекса).

### 5. Поиск — `src/rag/retriever.py`, функция `get_relevant_chunks`

Это **гибридный поиск**, не чисто векторный:

1. **Векторный кандидатный поиск** — FAISS находит ~20 ближайших по эмбеддингу кандидатов.
2. **Лексический скоринг — BM25** (`rank_bm25`, `BM25Okapi`) по всем документам. Раньше здесь была самодельная TF-IDF-подобная формула — заменена на BM25, который даёт то же самое "частый в документе, но редкий по корпусу термин важнее", но с насыщением по частоте термина (повторение слова даёт всё меньший прирост скора после некоторого порога) и нормализацией по длине документа — важно, так как аннотированные фрагменты лекций сильно разной длины (от короткой реплики до нескольких абзацев), а старая формула такую нормализацию не делала.
3. **Rank fusion** — оба списка объединяются через reciprocal rank (вектор даёт бонус `1/rank`, лексика — `2/rank`, то есть точным словам отдаётся больший вес), плюс добавляется сырой BM25-скор. Топ-5 после этого идёт в промпт.

**Почему не чисто векторный поиск:** точные русскоязычные термины (названия методов, специфичная лексика курса) иногда проигрывают по чистому косинусному сходству более общим, но семантически близким фразам. Лексический компонент — подстраховка против этого.

**Fallback без векторов:** если FAISS/эмбеддер недоступны, `get_relevant_chunks` полностью переключается на лексический поиск.

## Оценка качества — `scripts/eval_rag.py`

Изменения в чанкинге, промпте, embedding-модели и т.п. нельзя оценить на глаз — нужен фиксированный набор вопросов и метрика. `scripts/eval_rag.py` прогоняет `data/eval/questions.jsonl` (вручную составленные вопросы с эталонными ответами, `question`/`reference_answer`/`lecture_id`) через текущий RAG-пайплайн и считает [RAGAS](https://github.com/explodinggradients/ragas)-метрики: `faithfulness` (не выдумал ли ответ фактов сверх найденного контекста), `answer_relevancy`, `context_precision`, `context_recall` (нашёлся ли вообще нужный материал). Каждый прогон дописывается строкой в `data/eval/results.jsonl` с произвольным тегом и `--config key=value` — так разные конфигурации (чанкинг, top_k, модель) накапливаются в одном файле для сравнения по времени, без фиксированной схемы.

**RAGAS-судья — та же самая LLM, что используется и для генерации ответов** (`LM_STUDIO_MODEL` через LM Studio, `temperature=0.0`). Это важный источник шума при сравнении конфигураций: включение/выключение "Enable Thinking" в LM Studio меняет не только то, как модель отвечает, но и то, насколько строго она сама судит `context_precision`/`context_recall` — то есть сравнение прогонов с разным состоянием thinking конфаундится не только изменением поведения системы, но и изменением строгости судьи. Изолировать эффект конкретного изменения (например, чанкинга) стоит **в одном и том же reasoning-режиме**, а не сравнивая reasoning вкл/выкл как "какой лучше".

**Тестирование на подмножестве индекса, не трогая прод:**
- `scripts/embed_kb.py --annotations-dir ... --index-dir ...` — сборка индекса в отдельную папку, не `data/datasets/rag_index`.
- `RAG_INDEX_DIR` (env-переменная, `src/config.py`) — `src/rag/retriever.py` подхватывает её вместо дефолтного `data/datasets/rag_index`, так что `eval_rag.py` может смотреть в тестовый индекс без перезаписи продакшена.
- `eval_rag.py --lecture-id <id>` (можно повторять) — фильтрует `questions.jsonl` по `lecture_id`. Обязателен при eval на неполном индексе (например, только одна лекция) — иначе вопросы о лекциях, отсутствующих в тестовом индексе, будут ложно проваливать `context_recall` не из-за качества системы, а из-за того, что искать было физически негде.

**Разница между пилотом на одной лекции и полным корпусом:** индекс из одной лекции (~60 чанков) — гораздо более лёгкая задача для ретривера, чем полный корпус (~450+ чанков, 14 лекций) — меньше конкурирующих "шумных" кандидатов. На пилоте по одной лекции эффект от улучшения чанкинга может казаться сильнее, чем на полном корпусе (наблюдалось на практике: `context_recall` 0.19→1.0 на пилоте против 0.71→0.93 на полном корпусе) — числа с маленького индекса не стоит выдавать за финальную оценку без проверки на полном масштабе.

**Журнал всех прогонов при переходе на sentence-based чанкинг** (все таблицы метрик, по группам экспериментов, с выводами) — [EVAL_LOG.md](EVAL_LOG.md).

## Генерация ответа — `src/llm/chat.py`, `src/llm/model.py`

### Инференс-движок: LM Studio (план — vLLM на сервере)

Модель не встроена в код напрямую — `src/llm/model.py` обращается к локальному **OpenAI-совместимому серверу** (`POST /v1/completions`). Сейчас это LM Studio (движок — llama.cpp), при переезде на сервер планируется vLLM. Благодаря одинаковому API смена движка требует изменить только `LM_STUDIO_BASE_URL`/`LM_STUDIO_MODEL` в `.env` — код `chat.py`/`model.py` не меняется.

**Модель не фиксирована** — важное архитектурное решение: система рассчитана на любую instruct-модель, доступную через такой сервер (требования к минимальному размеру/контексту/квантизации — см. README).

**Почему raw `/v1/completions`, а не `/v1/chat/completions`:** так исторически сложилось (промпт собирается как один текстовый блок: системная роль + история + контекст + вопрос). Instruct-модели обучены именно на chat-формате (роли system/user), так что переход на `/v1/chat/completions` — вероятное улучшение качества следования инструкциям, в планах.

**Что уже даёт llama.cpp/LM Studio "бесплатно":** KV-cache, flash attention (если поддерживается GPU), квантизация модели (сейчас Q4_K_M). Батчинг в llama.cpp есть, но простой — не полноценный continuous batching уровня итераций, как в vLLM.

**Что добавит vLLM при переезде на сервер:**
- **PagedAttention** — управление KV-cache постранично (как виртуальная память ОС), устраняет фрагментацию, позволяет держать больше одновременных сессий на той же видеокарте.
- **Полноценный continuous batching** — новые запросы подключаются к уже работающему батчу на уровне отдельных шагов генерации, а не ждут завершения всего батча. Важно при ответах разной длины (от короткой реплики до полного объяснения с примером).
- **Prefix caching** — самая релевантная оптимизация именно для этой архитектуры: системный промпт длинный и одинаковый на каждый запрос, но пересчитывается заново каждый раз (prefill). vLLM умеет кешировать KV-состояния для одинакового префикса между запросами — считается один раз, а не на каждый вопрос. Требует явного включения (`enable_prefix_caching=True`), не работает "из коробки" без этого флага.
- **GPU-нативная квантизация (AWQ/GPTQ/FP8)** — как опция вместо GGUF, если понадобится больший throughput на конкретном железе.

Tensor parallelism (мульти-GPU) и speculative decoding рассматривались, но признаны не нужны на старте: первое требует нескольких GPU на сервере, второе усложняет setup без гарантированной отдачи для уже небольшой (4B) модели.

### Системный промпт — важный найденный баг (исправлен)

`SYSTEM_PROMPT` (`src/llm/chat.py`) раньше содержал внутреннее противоречие: одна инструкция запрещала выдумывать факты, а через несколько строк — **обязывала** сгенерировать "конкретный ситуационный пример" самостоятельно, с участниками/проектом/расчётом, которых нет в контексте. Модель честно следовала обеим инструкциям — писала грамотный ответ по контексту, а затем добавляла раздел "Пример" с полностью придуманными компаниями, ценами и числами. Это не было заметно при бедном, фрагментированном контексте (старый чанкинг) — модели "не хватало уверенности" на развёрнутую выдумку, — но резко проявлялось при богатом связном контексте (новый чанкинг): `faithfulness` в RAGAS-eval падал до ~0.73-0.81 против 1.0 после фикса. Требование генерировать пример убрано из `SYSTEM_PROMPT` и `build_rag_prompt`, добавлен явный запрет придумывать иллюстративные кейсы/компании/цифры вне контекста. Если такая "предложи учебный пример" функциональность понадобится снова — стоит делать её как факультативный, явно промаркированный раздел (не смешивая с основным, строго grounded ответом), иначе она снова будет искажать faithfulness-оценку.

### Постобработка ответа

- Ответ модели обрезается по маркеру `"Ответ:"` (если модель продублировала часть промпта — подстраховка, актуальная в основном для старого raw-completions подхода).
- Модельный вариант блока "Ссылки на лекции" вырезается (`_strip_model_sources`) — этот блок формируется кодом, не моделью, чтобы гарантировать точные таймкоды.
- Для итогового блока источников делается отдельный (короткий) вызов той же модели — сгенерировать 1-строчные саммари каждого источника; при недоступности модели используется эвристический fallback (`_fallback_source_description`).
- Если весь вызов модели упал (сервер не запущен и т.п.) — `_extractive_answer` собирает ответ прямо из найденных чанков без генерации, честно сообщая, что модель недоступна.

## Хранение видео и ссылки на источники

Требование — ответ должен ссылаться на источник так, чтобы пользователь мог перейти и посмотреть запись. Решение: **RAG-хранилище и видео-хранилище разделены.**

- **RAG (FAISS + meta.json)** хранит только текст, эмбеддинги и метаданные-указатели: `lecture_id`, `start_sec`, `end_sec`.
- **Видео/аудио** хранится отдельно (`data/raw/lectures/processed`), адресуется по `lecture_id`.

**Почему не хранить видео внутри RAG-индекса:**
- FAISS рассчитан на маленькие векторы, не на большие бинарники — смешение раздувает индекс, усложняет бэкап и версионирование.
- Раздача видео требует своей инфраструктуры (файловый сервер, объектное хранилище S3/MinIO, возможно HLS для перемотки) — совершенно другой слой системы, чем векторный поиск.
- Раздельное хранение позволяет менять способ хранения видео (локально → объектное хранилище → куда угодно) без изменения схемы RAG-индекса — ему нужен только стабильный `lecture_id`/URL + таймкод.

Таймкоды (`start_sec`/`end_sec`) уже есть в текущей схеме данных с этапа транскрибации — для реализации кликабельных ссылок не хватает только (1) эндпоинта, раздающего видео по `lecture_id`, и (2) функции в `chat.py`, которая строит URL с таймкодом (`/video/{lecture_id}?t={start_sec}`) для блока "Ссылки на лекции". На момент написания документа это не реализовано.

## Легаси-компоненты (не часть активного пайплайна)

Не вызывайте эти скрипты как часть основного пайплайна — они относятся к более ранней версии проекта:

- `scripts/backfill_segments_from_transcripts.py` — восстанавливает `.segments.jsonl` из `.txt`-транскриптов на случай, если сегменты были потеряны; текущая транскрибация (`whisper_transcriber.py`) пишет оба формата сразу, так что в норме этот скрипт не нужен.
- `scripts/build_annotation_drafts.py` — старая пауза/длительность-эвристика чанкинга (см. раздел "Разметка на смысловые блоки"). Не удалён — оставлен для сравнения и как референс для будущих альтернативных стратегий, но `scripts/ingest_lectures.py` его больше не вызывает.
- `scripts/generate_annotations.ps1` — PowerShell-обёртка над старой пауза-эвристикой, без LLM. Не переведена на sentence-based чанкинг (используется редко, для отладки без Python-окружения).

Удалено как неиспользуемое: `scripts/clean_transcripts.py` и папка `data/cleaned/` — чистили `data/transcripts`, но результат никуда дальше не использовался (индексация всегда читала `data/annotations`, не `data/cleaned`).

**Бэкап старой прод-версии данных** (после перехода на sentence-based чанкинг): `data/annotations_old_pause/`, `data/drafts_old_pause/`, `data/datasets/rag_index_old_pause/` — полная копия прод-данных на старом чанкинге, на случай отката. Можно удалить, когда новая версия подтвердится в реальном использовании.

## Открытые вопросы / Roadmap

Зафиксированные в обсуждениях направления развития, ещё не реализованные:

1. Чанкер для структурированных документов (пособий), отдельный от чанкера транскриптов.
2. Semantic-чанкинг (векторизовать предложения, резать по спаду косинусной близости между соседними) и рекурсивный чанкинг — как альтернативные стратегии поверх `scripts/chunking/timed_sentences.py`, для сравнения с текущим sentence-based подходом через `scripts/eval_rag.py`.
3. Переход на `/v1/chat/completions` вместо raw `/v1/completions`.
4. Переезд инференса на vLLM (сервер), с `enable_prefix_caching=True`.
5. Раздача видео по `lecture_id` + таймкод-ссылки в ответах бота.
6. Удалить `*_old_pause` бэкапы после подтверждения стабильности нового чанкинга в реальном использовании.

Реализовано:
- Замена захардкоженных `TOPIC_PATTERNS` в `prefill_annotations.py` на LLM-вызов с fallback на эвристику (см. раздел "Заполнение метаданных" выше) — включая компенсацию ошибок ASR через лёгкую очистку текста.
- Смена embedding-модели с англоцентричной MiniLM на multilingual (`nomic-embed-text` через LM Studio) — см. раздел "Индексация".
- Замена самодельного лексического скоринга на BM25 (`rank_bm25`) — см. раздел "Поиск".
- Замена пауза/длительность-чанкинга на sentence-based (`scripts/build_annotation_drafts_by_sentence.py`) — см. раздел "Разметка на смысловые блоки". Обосновано численно через `scripts/eval_rag.py`: `context_recall` 0.71→0.93 на полном корпусе.
- RAGAS-based eval harness (`scripts/eval_rag.py`, `data/eval/`) — см. раздел "Оценка качества".
- Исправлен баг системного промпта, из-за которого модель обязательно выдумывала иллюстративный пример вне контекста — см. раздел "Системный промпт" выше.
